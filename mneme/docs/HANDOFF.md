# 引き継ぎ: 特化AIアーキテクチャ研究(MNEME)→ ローカルPCセッション

## 0. この文書は何か

クラウドセッション(リポジトリ `ikuto-yamaguchi/python`、ブランチ
`claude/specialized-ai-architecture-3ytozh`)で行った研究開発の引き継ぎ。
引き継ぎ先はローカル PC(GPU あり)で動く Claude Code セッション。
最終目的は、ユーザーが**別チャットで進めている「C0 テスト特化 AI」
(ローカル GPU で 1B 級モデルを蒸留中、上手くいっていない)**と
この研究を合流させること。

**重要**: クラウド側は別チャットの内容を一切見ていない。仕様は推測で
進めて叱られた。ローカルセッションは必ず先に §4 のヒアリングをすること。

## 1. ユーザーの問題意識(このセッションで確認済み)

- トークナイザーは特化 AI にとって非効率。賢い知能と正確で大量の記憶が
  あれば、複雑なタスクは少ないリソースでこなせるはず
- 1B ですら大きすぎる疑い。特化 AI なら 100M 級で軽量・高速に動くべき。
  現行の 100M トランスフォーマーがエージェントタスクで使い物に
  ならないのは「能力の下限」ではなく「アーキテクチャの非効率」のはず
- ローカル GPU での 1B 蒸留が不調(症状・仕様は未聴取)

## 2. 議論で固まった設計理論(結論のみ)

1. **分離できる線は「知能|記憶」ではなく「スキル(重み)|知識(外部ストア)」**。
   事実・エピソード・手順は外部記憶に置けば勾配ゼロで追加・編集できる。
   スキル(理解・推論)は重みそのものであり外部化できない
2. **アテンションは「機構」ではなく「機能(内容アドレッシング)」が必須**。
   密なグローバルアテンションは不要で、再帰コア(GRU/Mamba 系)+
   外部 top-k 検索 + 必要なら短窓ローカルアテンションで全項を線形以下にできる
3. **理解のコストはタスクの難しさではなく「インターフェースの広さ」に比例する**。
   1B が要るのは開放自然言語を受ける約束の税金。インターフェースを閉じれば
   激減する(実在証明: AlphaZero、チェス NNUE、TinyStories)
4. **100M(以下)特化エージェントの成立条件**:
   (a) 閉じたインターフェース(入力をドメインの部分言語に制限)
   (b) 知識・手順の外部化(エピソード記憶、勾配ゼロで蓄積)
   (c) 推論時探索(提案→実行→観測のフィードバックループで
       パラメータ不足を実行回数で補う)
   (d) 実行検証つきの密な学習信号(Web 模倣ではなくタスクの合否で学習)
5. **1B 蒸留が失敗する典型**(仮説、要診断):
   開放インターフェースのまま蒸留している / 教師データの信号が薄い。
   対策は「タスク分布に絞った教師データ + 実行検証フィルタ
   (生成テストを実際に走らせ、カバレッジが上がった軌跡だけを教師データ化)」

## 3. 実証済みの結果(このリポジトリ、全て CPU、全て合成タスク)

コードは `mneme/` 配下。`pip install torch` のみで動く。

### 実験 1: 知識想起 — 外部記憶 vs パラメータ焼き込み(同規模 ~0.7M)

| 事実数 N | 外部記憶(勾配 0 step) | パラメータ焼き込み(2000 step 再学習) |
|---:|---:|---:|
| 64〜1024 | 93.8〜96.5% | 100% |
| 4096 | **94.3%** | **8.3%(容量崩壊)** |

→ 知識はパラメータ外に置けて、量に対してコストが増えない。

### 実験 2: エントロピー動的パッチング(トークナイザー置換)

約 7 万パラメータのバイト LM で次バイト予測エントロピーの跳ねる位置を
境界にする。ドメイン内 5.21 bytes/patch(コアの O(L²) は約 1/27)。
語彙表ゼロ。ドメイン適応は推定器の差し替えのみ。

### 実験 3: C0(命令網羅)テスト生成特化エージェント ★C0 AI に直結

対象: 整数引数 + 比較条件 if/elif/else 木の合成関数 40 個(閉じた部分言語)。
エージェントは未カバー行の到達条件テキストを読み、充足入力を提案→実行→
カバレッジ観測のループ。知能コアは条件バイト列→充足値の **0.72M** ソルバ
(学習 76 秒/CPU、ホールドアウト充足率 100%)。

| 方式 | C0 平均 | 100% 達成 | 平均実行回数 |
|---|---:|---:|---:|
| ランダム探索(2000 実行) | 92.7% | 14/40 | 1425.9 |
| エージェント(条件を読まない) | 78.3% | 0/40 | 48.8 |
| + ソルバ 0.72M | **100.0%** | **40/40** | 15.3 |
| + ソルバ + 外部記憶 | **100.0%** | **40/40** | **13.9** |

→ 「条件を読む」極小コアの価値が定量化できた。1B どころか 0.72M。
ただし**対象はおもちゃの部分言語**。実コード対応はここから。

## 4. 最初にユーザーへヒアリングすること(未確認事項)

1. 別チャットの C0 AI の**入出力仕様**(何を入れると何が出る?
   実 Python コード? pytest 生成? カバレッジ計測は何で?)
2. **蒸留の構成**: 教師モデル / 生徒 1B のベース / データの中身と量 /
   SFT か logit KD か / 学習設定
3. **不調の症状**: 損失が下がらない / 出力が壊れる / カバレッジが
   上がらない、のどれか。ログ・損失曲線
4. **ローカル環境**: GPU と VRAM、フレームワーク(PyTorch? llama.cpp?
   unsloth?)、モデルの置き場

## 5. ローカルセッションの提案タスク(優先順)

1. §4 のヒアリング。別チャットの成果物(スクリプト・データ)の場所を
   聞いてリポジトリ or 作業ディレクトリを把握する
2. **蒸留の診断と立て直し**(§2-5 の仮説を検証):
   教師データを C0 タスク分布に絞る / 実行検証フィルタを挟む /
   評価をカバレッジ達成率など実タスク指標にする
3. **実コード版 C0 エージェント**: `mneme/c0/` の設計
   (coverage 計測 = 環境、条件充足 = モデル、記憶 = 関数横断キャッシュ、
   実行フィードバックループ)を実 Python に拡張する。
   - カバレッジ: `coverage.py` ライブラリ or `sys.settrace`
   - 条件抽出: AST(既存 `guard_chains` の一般化)
   - ソルバ: 0.72M GRU では実コードの条件(式・文字列・複数変数)に
     足りないので、蒸留中の生徒モデル or 数百 M 級小型 LM に置き換え、
     **ループと記憶はそのまま**使う。ここが 1B 蒸留との合流点
4. **比較実験**: 「1B 単発生成」vs「小型モデル + 実行フィードバック
   ループ + 記憶」で、カバレッジ・実行回数・レイテンシ・VRAM を比較。
   ユーザーの仮説(ループと記憶があれば小さいモデルで足りる)の検証

## 6. リポジトリの使い方

```bash
git clone https://github.com/ikuto-yamaguchi/python
cd python && git checkout claude/specialized-ai-architecture-3ytozh
pip install torch  # CPU 版で全部動く

cd mneme
python tests/test_mneme.py                  # 基盤テスト 7 件
python tests/test_c0.py                     # C0 エージェントテスト 7 件
python experiments/run_c0_benchmark.py      # 実験 3 の再現(数分)
```

設計の詳細は `mneme/docs/ARCHITECTURE.md`、結果の詳細は `mneme/README.md`。
