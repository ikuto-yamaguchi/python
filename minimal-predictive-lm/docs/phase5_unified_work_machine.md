# Phase 5: Unified Minimal Work Machine

## 目的

最終目標を、単なる次トークン予測器ではなく、次の仕事を同じ最小機械で実行できることに置く。

- コーディング: リポジトリ理解、修正案生成、テスト、デバッグ、ツール操作
- 文章作成: 意図理解、構成、事実整合、文体制約、推敲
- エージェント: 状態観測、目標分解、計画、外部操作、結果確認、再計画

ただし、能力ごとに別の内部表現・記憶・推論器を後付けしない。追加能力は原則として、**一つの正準状態と一つの書換え機械上のプログラム**として表現する。

## 後付け肥大化の原因

機能数そのものより、同じ情報を複数形式で保持することが大きな無駄になる。

悪い構成:

```text
言語モジュールの埋め込み
  -> 記憶モジュール用ベクトルへ変換
  -> 推論グラフへ変換
  -> planner状態へ変換
  -> agent tool schemaへ変換
  -> 出力LMへ再変換
```

この構成では、同じ人物・目的・制約・進捗が各モジュールに重複し、境界ごとに変換・コピー・整合性確認が必要になる。

統一構成:

```text
正準シンボル
+ 型付き疎な事実
+ 書換え規則
+ 目標・制約・コスト
+ provenance
```

すべての能力がこの一つの状態を直接読む。

## 能力はモジュールではなく同じ演算の異なる使い方

- 意味理解: 入力事実を正準事実へ書き換える
- 長期記憶: 事実を保持し、更新・撤回する
- 推論: 規則を適用して新しい事実を導く
- 計画: 目標に近づく書換え列を探索する
- 創造: 新規性を優先した書換え列を探索する
- 学習: 予測残差を減らす規則を追加し、不要規則を削除する
- 文章作成: 意味・談話制約を満たす出力列を構成する
- コーディング: AST・型・テスト結果へ書換えを適用する
- エージェント: 外部作用を持つ書換えを実行し、観測を事実として戻す

創造と論理、計画と文章生成を別エンジンにせず、探索の目的関数と許可する書換えを変える。

## 最小ランタイム命令

Phase 5aでは、まず次の5命令だけを共有する。

```text
MATCH       必要な疎事実が存在するか確認
DELETE      無効になった事実を除去
ADD         新しい事実を追加
EMIT        出力シンボルを追加
CHOOSE_MIN  累積記述長が最小の実行列を選択
```

将来、外部環境との境界として次を一つだけ追加する可能性がある。

```text
EFFECT      ツール実行または環境操作を行い、結果を事実として返す
```

`memory`、`stack`、`counter`、`planner`、`creativity`、`AST editor` は最初からネイティブ命令にしない。既存命令のマクロとして表し、コンパイラが特殊化する。

## 抽象化の実行時コストを残さない

統一IRは研究・学習には便利でも、汎用インタプリタのまま実行すると遅い。そこで二段階に分ける。

```text
学習・探索:
  汎用の疎グラフ書換えIR

コンパイル:
  定数伝播
  不要事実削除
  規則融合
  部分評価
  状態最小化
  頻出経路の直接遷移化

実行:
  対象ワークロードへ特殊化された小さな状態機械 / bytecode
```

能力を統一するのはランタイムを汎用化するためではなく、**学習時の重複表現をなくし、最後に全抽象化をコンパイルで消すため**である。

## 新しいプリミティブの採用条件

新しい命令や専用データ構造を追加する場合は、次を満たさなければならない。

```text
既存命令で表した場合の生涯コスト
-
新プリミティブ導入後の生涯コスト
>
新opcodeの記述bit
+ compiler実装bit
+ serializer実装bit
+ 追加表現変換bit
+ 保守・検証コスト
```

一つのベンチマークだけ速くなる専用機能は、原則としてマクロのまま保持する。複数の対象仕事で繰り返し使われ、総コストを下げるときだけネイティブ化する。

## Phase 5a 実証

コーディング、文章作成、エージェント計画の小さな問題を、同じ以下の実装で解く。

- 一つの `SymbolTable`
- 一つの `State`
- 一つの `Rule`
- 一つの疎規則index
- 一つの最小記述長探索器

### Coding

テストから `f(x)=a*x+b` の最小修正を選ぶ。AST候補とテスト結果は事実へコンパイルされ、最短の全テスト通過パッチを選ぶ。

### Writing

必要内容、順序、文体を事実として与え、条件を満たす最小出力プログラムを選ぶ。

### Agent

場所・接続・所有状態を同じ事実形式で与え、目標事実を成立させる最小行動列を選ぶ。

この実験の難易度は低い。目的は、三つの能力が別エンジンを要求しないことを実装で確認することにある。

## 最終目標に向けた評価セット

研究開始時点から、次を同じ評価関数に入れる。後から能力を追加しない。

### コーディング

- 未知リポジトリの局所修正
- 複数ファイル依存
- テスト失敗からの修正
- 型・ビルド・静的解析
- ツール結果を受けた再計画
- パッチbit、読んだコードbit、実行したテスト数、命令数

### 文章

- 要件を満たす説明文
- 長文の論旨・参照一貫性
- 事実制約と文体制約
- 改稿と差分編集
- 新規性と適切さ
- 読んだ知識bit、談話状態bit、候補数、出力命令数

### エージェント

- 部分観測環境
- 長期タスク
- 失敗復旧
- 外部ツール呼出し
- 副作用確認
- 観測bit、行動数、再計画数、動的状態bit

## 統合目的関数

対象ワークロード分布 `W` に対し、次の期待生涯コストを最小化する。

```text
answer / task loss
+ static program bits
+ static knowledge bits
+ expected dynamic state bits
+ expected bits read
+ expected bits written
+ expected primitive operations
+ expected external effects
+ compiler/search cost / deployment count
+ representation-boundary cost
```

特に `representation-boundary cost` を明示的に入れる。同じ情報を別モジュール形式へ変換した場合、そのコピーbit、変換命令、同期処理をすべて課金する。

## 研究上の禁止事項

- 新しい能力ごとに別の埋め込み空間を作る
- 記憶、推論、計画で同じ事実を重複保存する
- 「小さい補助モデルだから」とニューラル重みを無料扱いする
- 汎用IRのインタプリタ overhead を最終性能から除外する
- 外部検索・テスト・ツール呼出しを計算量から除外する
- 評価に失敗した機能を専用モジュールで即座に継ぎ足す

## 次の研究段階

1. Phase 5a: 同じ5命令でcoding / writing / agentのmicro-taskを解く
2. Phase 5b: 一つの状態を共有する複合タスク
   - 仕様文を読む
   - コードを修正する
   - テストする
   - 結果報告を書く
3. Phase 5c: `EFFECT`を追加し、ツール実行を含む長期タスクを扱う
4. Phase 5d: 汎用書換えIRを部分評価し、タスク専用状態機械へ自動コンパイル
5. Phase 5e: プリミティブ追加・削除を生涯MDLで自動決定

Phase 5bが重要である。文章理解、コーディング、ツール利用、報告作成を一つのepisode内で実行し、同じ目標・事実・provenanceを一度だけ保持できるかを検証する。
