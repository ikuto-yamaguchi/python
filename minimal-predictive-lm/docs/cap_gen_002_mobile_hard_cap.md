# CAP-GEN-002 mobile hard-cap architecture

## Absolute requirements

These are rejection constraints, not optional optimization goals.

- The complete deployed artifact, including learned weights, routers, persistent semantic and episodic memory, metadata, and codec state, must be at most **1,000,000,000 bytes**.
- A real low-end Android ARM64 device with at most 4 GB physical RAM must keep peak RSS at or below **384,000,000 bytes**.
- First generated byte must arrive within **300 ms**.
- Sustained generation must reach at least **60 UTF-8 byte steps/s** and p95 step latency must remain at or below **20 ms**. For ordinary Japanese this is roughly 20 characters/s before text segmentation improvements.
- Static operation budget is at most **2,000,000 MACs per byte step** and active weight traffic at most **4,000,000 bytes per step**.
- Japanese high-school intelligence remains false until the frozen curriculum, unseen transfer, written-answer, correction, long-document, and repository-work gates pass.

## Architecture change

A dense model near the 1 GB limit would force a weak phone to stream most weights for every generated token. That is prohibited. The new reference uses hierarchical routing and memory-mapped int8 blocks.

The serious profile contains 8,192 recurrent specialist blocks but activates only two for each byte step. One coarse group and two fine blocks are selected without a task or benchmark name. Each block contains an input map, low-rank recurrent transition, and byte decoder. An LRU state cache keeps only a small working set resident.

### Serious profile accounting

- complete planned package: **905,003,008 bytes**
- active weight traffic: **238,080 bytes/byte step**
- estimated arithmetic: **237,568 MACs/byte step**
- recurrent state cache: **32,768 bytes**
- active blocks: **2 / 8,192**

The remaining space below 1 GB is intentionally reserved for package indexes, tokenizer evolution, calibration, and format overhead. The model is not allowed to exceed the decimal 1 GB ceiling by calling it 1 GiB.

## Runtime path

`native/mobile_sparse_kernel.c` is an allocation-free generic C99 int8 token-step kernel. It is suitable for Android NDK compilation and makes token-step compute depend on active blocks rather than total model capacity. The current implementation is portable scalar C. NEON kernels may replace inner products only when numerical parity and the same resource gates remain intact.

The Python `MobilePagedSparseCore` is a trainable reference for routing, recurrent state, local feature updates, chat execution, and accounting. It is not used as proof of smartphone speed.

## Mandatory device evidence

Host CI timing is reported only as a mechanics check. It can never set `mobile_device_gate_passed=true`. Promotion requires a benchmark record from a real device declared as `weak-android-phone`, running Android on ARM64 with at most 4 GB RAM, and satisfying every latency, throughput, memory, and package-size requirement.

## Conversation status

`mpm-mobile-chat` provides an executable interaction path and can load prompt/response teaching data. It exists to keep the model continuously conversational during development. Its current tiny CI checkpoint is not the requested intelligence model and explicitly says so. The same mobile architecture must be trained on mixed Japanese language, mathematics, science, humanities, code, correction, and dialogue data and then pass the unchanged broad gates.

## Next capability experiment

1. Replace byte-only generation with a compact learned UTF-8 segment codec without expanding the package ceiling.
2. Train hierarchical routing jointly with recurrent blocks on mixed raw curriculum and dialogue streams.
3. Export an mmap-backed int8 checkpoint using the serious profile.
4. Build the C99 kernel with Android NDK and benchmark it on a real low-end ARM64 phone.
5. Run the same checkpoint on the axis-blind integrated public suite and Japanese high-school target. Any speed gain that destroys broad capability, or capability gain that violates mobile limits, is rejected.
